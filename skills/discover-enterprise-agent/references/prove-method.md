# PROVE：企业 Agent 场景发现与定义方法

PROVE 是本 Skill 的内部推理方法，不必作为对外标题。它融合了“我是谁—从哪来—到哪去”的角色建设视角，并把企业真实流程、产品边界和验证闭环前置。

## 一、五个步骤

| 步骤 | 核心问题 | 必须形成的判断 | 常见错误 |
|---|---|---|---|
| P — Process evidence 流程证据 | Agent 从哪段真实流程中产生？ | 关键流程、真实角色、任务/决策、核心输出、系统数据、痛点 | 从模型能力或产品功能倒推场景 |
| R — Role formation 角色成形 | 哪些能力应组成一个稳定角色？ | 服务对象、角色使命、责任循环、流程范围、进入/退出点、拆并结论 | 一个场景一个 Agent，或所有能力装进一个助理 |
| O — Outcome contract 结果契约 | Agent 要交付什么可使用结果？ | 输入、核心输出、使用者、下一步动作、质量要求、人机边界 | 只写“提效赋能”，没有业务产物 |
| V — Value & viability 价值与可行性 | 值不值得建、现在能不能建？ | 真实任务验证、业务价值、采用意愿、数据/知识准备度、风险、基线 | 先填漂亮指标，后找验证任务 |
| E — Evolution 演进 | 如何从单点角色扩展为能力体系？ | 一期最小闭环、成熟度路径、共享能力、角色家族、治理机制 | 一期就设计完整数字员工组织 |

## 二、与“我是谁—从哪来—到哪去”的关系

| 角色建设表达 | PROVE 提供的证据 |
|---|---|
| 我是谁 | R 定义角色，O 定义角色可交付的结果 |
| 从哪来 | P 映射企业真实流程，不照搬通用周期模型 |
| 到哪去 | V 验证经营力与业务力，E 规划成熟度和角色体系 |

“三力九度”等评价框架可以作为“到哪去”的评估目录，但不能替代流程、角色和结果定义。尚未完成数据、模型、系统、安全评估时，保留标题并写 `待评估`。

## 三、事实层级

所有分析内容标记为以下三类之一：

- **已确认事实**：来自企业流程、制度、系统、数据、访谈或用户明确说明。
- **设计判断**：基于事实提出的产品设计建议，要说明理由。
- **待确认项**：会改变角色边界、一期范围或风险结论的信息缺口。

不得把设计判断包装成企业现状。

## 四、角色拆分判据

优先保持一个角色，除非出现两个或以上实质差异：

1. 角色使命不同；
2. 主要服务对象或责任人不同；
3. 核心业务对象不同；
4. 工作节奏和触发方式不同；
5. 进入/退出的流程边界不同；
6. 输出被不同决策或动作消费；
7. 权限、风险或问责链不同。

以下情况通常不足以单独拆分 Agent：

- 使用了不同模型或工具；
- 数据来自不同系统；
- 一个能力是检索、另一个是计算；
- 能力分布在相邻流程节点；
- 同一个结果有多种呈现载体。

## 五、能力命名

能力名称采用“业务对象 + 动作/判断”，例如：

- 公开 Tender 持续发现；
- Tender 信息结构化；
- 商机资格初判；
- 竞争证据检索；
- ROI 快速测算；
- 客户价值摘要生成。

避免直接使用“智能问答、知识库、RAG、大模型、工作台”等技术或载体名称代替业务能力。

## 六、验证优先级

一期优先验证一条真实任务链：

```text
真实输入 → Agent 产出 → 人工判断/动作 → 结果反馈
```

每个指标必须回答一个验证问题：

| 验证问题 | 可选指标 |
|---|---|
| 是否节省了关键任务时间？ | 首次产出耗时、人工整理耗时 |
| 输出是否可直接使用？ | 采用率、人工修改率、退回率 |
| 结论是否可信？ | 来源覆盖率、事实错误率、假设透明度 |
| 是否进入真实流程？ | 目标任务处理率、后续动作发生率 |
| 能否稳定扩展？ | 数据覆盖率、异常率、单位任务成本 |

没有基线、样本或采集机制时，先写“待建立基线”，不要给虚假目标值。
